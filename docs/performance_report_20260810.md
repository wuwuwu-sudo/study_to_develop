## 6. 🐛 压测中发现并修复的真实缺陷

### 问题
`HttpServer::use()` 只把中间件收集进 `middlewares_` 向量，但请求处理路径 `handle_client_data()` 只调用了 `router_.dispatch()`——**日志 / 限流 / 认证三个中间件从未在请求链路中执行**。表现：限流恢复后验证时始终不触发 429。

### 修复
1. `MiddlewarePipeline::execute()` 增加 `final_action` 参数（默认 `nullptr`，兼容原有 2 参调用与测试）
2. `HttpServer` 改用 `MiddlewarePipeline pipeline_` 成员
3. 请求路径改为：
   ```cpp
   pipeline_.execute(request, response, [this, &request, &response]() {
       router_.dispatch(request, response);
   });
   ```
4. 三个中间件经验证均线程安全（Logging 无状态、Auth 路径列表仅启动前配置、RateLimit 自带互斥锁、Pipeline 只读遍历），可安全在 8 线程池中并发执行

### 验证
- 编译通过，**315 个单元测试全部通过**
- 限流 100/60/300 生效：发 103 请求 → 100×200 + 3×429，限流警告日志 3 条一一对应
- 日志中间件开始逐请求输出 `GET / -> 200 (0ms)`

## 7. 性能瓶颈与优化建议

中间件生效后吞吐下降 2~3 倍，两大瓶颈：

1. **限流中间件全局互斥锁**：`RateLimitMiddleware::handle()` 每请求持 `impl_->mutex`，把 8 个工作线程的请求处理**串行化**。
   - 建议：改用分片锁（striped lock）或每核独立计数后合并。

2. **日志中间件同步写文件 + flush**：`Logger` 每请求向 `ofstream` 写一行并 `flush`，磁盘 IO 成为热点。
   - 建议：改**异步日志**（内存队列 + 独立写线程批量落盘），或降低日志级别 / 关闭控制台输出。

3. **连接不复用**：服务器每次响应后 `close()`，无法 keep-alive 复用 TCP 连接，产生大量建连开销。
   - 建议：实现 HTTP/1.1 keep-alive，QPS 可进一步显著提升。
