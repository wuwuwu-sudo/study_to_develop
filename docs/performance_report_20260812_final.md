## 6. 多级缓存分层验证（L1 / L2 / L3）

整个测试期累计处理 **千万级请求**，Redis 侧统计：

| Redis 指标 | 数值 | 含义 |
|-----------|------|------|
| `total_commands_processed` | **123** | L1 本地缓存吸收了几乎全部稳态流量 |
| `keyspace_hits` / `misses` | 66 / 14 | L2 仅在 L1 过期 / 冷启动时被命中（兜底） |
| 缓存 key | `dish:merchant:1:paged:1:10`（TTL 动态衰减） | 写回缓存正常 |

```
GET /api/dishes?merchant_id=1
   → L1 本地内存（60s TTL）          ← 承载 ~100% 稳态流量
   → 未命中 → L2 Redis（300s TTL）   ← L1 过期后兜底
   → 未命中 → L3 SQLite              ← 回填 L2 + L1
```

写操作按商家前缀同时清除 L1 + L2，保证不读脏数据。多实例部署时 L2 跨进程共享价值更大。

## 7. 性能瓶颈与优化建议

已完成的关键优化（均经 A/B 实测验证）：
1. **三级缓存**：读路径命中 L1，免 DB 往返。
2. **批量异步日志**：flush 频率降 40 倍，system CPU -15%。
3. **限流锁最小化**：`next()` 移出锁，消除完整请求串行化（c=64 QPS 14k→28k）。
4. **HTTP/1.1 keep-alive + TCP 心跳**：消除每请求建连开销（c=64 QPS 28k→63k），socket 错误归零。

当前瓶颈（按影响排序）：
1. **事件循环单线程**：约 90k QPS 时主线程 epoll 分发成为新上限（高并发下 wrk 超时与事件循环饱和相关）。
   - 建议：多 epoll 实例 + `SO_REUSEPORT` 分片，或事件循环任务进一步减负。
2. **静态文件同步读 + 用户态拷贝**：`send_file` 仍整文件读入内存再发。
   - 建议：改用 `sendfile()` 零拷贝，降低大文件场景开销。
3. **锁原子操作**：LocalCache / 连接表等短持有锁在高 QPS 下仍有缓存行乒乓。
   - 建议：LocalCache 分片锁；连接表用无锁或读写锁。

多级缓存本身已不是瓶颈（L1 命中路径极快、RSS 恒定、无泄漏）。

```bash
# 1. 生成临时高限流配置
sed 's/^server.rate_limit.max_requests=.*/server.rate_limit.max_requests=100000000/' \
    src/shared/config.json > /tmp/bench_config.json

./webserver --port 8090 --config /tmp/bench_config.json

# 3. 预热缓存（填满 L1 + L2）

wrk -t8 -c128 -d30s --latency \
  'http://127.0.0.1:8090/api/dishes?merchant_id=1&page=1&page_size=10'

# 5. 验证 L2 参与
redis-cli KEYS 'dish:merchant:*'

```
