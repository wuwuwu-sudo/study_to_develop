# webserver 单实例性能测试报告（2026-08-17）

- **测试日期**：2026-08-17
- **工具**：wrk 4.2.0（~/.local/bin）+ pidstat / procfs（RSS/fd）+ redis-cli
- **服务器版本**：release 构建（C++17, epoll + 8 线程线程池 + SQLite 连接池 16 + WAL）
- **本版相对 8/15 的优化**（2026-08-16 落地 + 8/17 当日补充）：
  1. **writev 拆分响应头/体发送**（省一次 body 整串 memcpy）
  2. **每线程复用 request/response + 序列化缓冲**（`static thread_local`，headers 桶 reserve，跨请求复用容量）
  3. **延迟缩容 DelayedShrink**（thread_local 缓冲保留历史峰值容量，连续 1000 次小用才缩容）
  4. **菜品分页字符串直出**（8/17 同日方案 A：缓存命中零解析，`/api/dishes` 58.4k → 95k，见 §7-4）
  5. **对象池/内存池已移除**（`ObjectPool<ChainState>`+`SmallPool` A/B 实测对 CPU/QPS 中性，已删源码；`middleware.cpp` 改纯栈上 `ChainState`，闭包仍 16B SBO 零堆分配，见 §8 附注）
- **被测实例**：单实例 8081（8082/8083 已停止；Nginx 网关运行中，`/var/log/nginx/food_delivery/` 日志已于当日清空）
- **压测目标**：QPS、响应延迟、最大并发连接数、资源消耗、长时间稳定性、缓存分层

## 7. 性能瓶颈与优化建议（当前版本）

1. **系统态 %system ~171% 为首要成本**：`recv`/`send` 网络 syscall + 日志落盘。
   - 建议：日志级别下调/抽样；网络侧依赖 Nginx `sendfile`/`open_file_cache`（已部署）；写路径 `writev` 已落地，可进一步在连接级做 `sendmsg` 批量。

2. **锁（线程池/连接表）**：LocalCache 分片锁已消除缓存争用，剩余来自 `ThreadPool::enqueue→cond_signal` 与连接表。
   - 建议：线程池**批量唤醒**（`enqueue_batch` + 一次 `notify_all`）；连接表哈希分片；三实例时 `thread_pool_size` 与 8 核匹配。

3. **内存分配**：thread_local 复用已显著降 RSS（-23%），剩余每请求分配集中在 DTO/函数对象。
   - 建议：热点路径进一步 `reserve` 预分配，避免再次引入全局分配器替换（此前 SlabPool 实测相对 glibc tcache 回归 -10~-15%，已回退）。

4. **`/api/dishes` 相对 8/15 下降（68.3k → 58.4k）——已定位并优化落地**（详见 `docs/perf_report_20260817_dishes.md`）。
   - **根因**：`/api/dishes` 走"对象型缓存"——缓存命中后每请求仍 `parse` 回 DTO + handler 手工重建 json + `dump` 序列化 + 析构（JSON 相关用户态 ~15%、内存分配/释放 ~18%），而 `/api/shops` 是"字符串直出"（缓存字符串直接 `set_json`，零解析）。
   - **优化落地（方案 A）**：新增 `DishService::get_dishes_paged_serialized()` 字符串直出（独立 `:resp` 缓存 key，失效同前缀），handler 缓存命中直接 `set_json`。perf 复测：JSON 热点完全消失、用户态采样 1.49MB→0.76MB（-49%）、malloc -80% / cfree -75%；压测 c=128 **58.4k → 95-100k（+60%+）**；全量测试 376 通过（对象池移除后）。

## 9. 复现方法

```bash
# 0. 清理 nginx 日志（需 sudo，避免磁盘写满）
sudo truncate -s 0 /var/log/nginx/food_delivery/access.log
sudo truncate -s 0 /var/log/nginx/food_delivery/error.log

# 1. 启动 Redis（L2 缓存）
redis-server --daemonize yes --port 6379

# 2. 启动单实例（高限流配置）
sed 's/server.rate_limit.max_requests=100/server.rate_limit.max_requests=10000000/' \
    config/instance_8081.json > /tmp/bench_single.json
./webserver --port 8081 --config /tmp/bench_single.json &

# 3. QPS / 延迟（单路 wrk，直连 8081，8s/档）
python3 tools/bench_single.py "/"                 8 4 "1,8,16,32,64,128"
python3 tools/bench_single.py "/api/shops"        8 4 "1,8,16,32,64,128"
python3 tools/bench_single.py "/api/dishes?merchant_id=1" 8 4 "1,8,16,32,64,128"

# 4. 最大并发
for c in 256 512 1024 2048 4096 8192; do wrk -t8 -c$c -d8s --latency http://127.0.0.1:8081/api/shops; done

# 5. 资源采样（60s @ c=128，webserver PID 用 pgrep 获取）
wrk -t4 -c128 -d60s http://127.0.0.1:8081/api/shops &
pidstat -p $(pgrep -f 'webserver --port 8081' | head -1) -u -r 5 12

# 6. 稳定性（3×60s @ c=64）+ Redis 命令增量
wrk -t4 -c64 -d60s http://127.0.0.1:8081/api/shops
redis-cli info stats | grep total_commands_processed   # 前后对比增量
```
