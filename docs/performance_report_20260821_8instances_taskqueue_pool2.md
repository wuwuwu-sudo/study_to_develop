## 3. 差异分析

1. **RSS 下降 -25%（81.9MB → 61.2MB）是本次最显著、最确定的收益**：
   - 直接归因于 **`db.pool_size` 16→2**——每进程 SQLite 连接从 16 个降到 2 个，8 进程共 128→16 个连接，每连接的开销（句柄、缓冲、WAL 关联结构）随之减少 ~2.6MB/实例。
   - 与单锁改造无关（锁本身不占内存），验证了此前「pool_size=16 过度配置」的判断。

2. **合计 QPS +7.0%（150.4k → 160.9k）需谨慎归因**：
   - 两轮**测试环境不同**：旧版在负载噪声大时测（期间 load 峰值 15+），新版在 **load 0.38 干净**时测——环境更干净本身就会抬升 QPS。
   - 内存下降（换页更少）也可能小有贡献；单锁 vs 16 片锁在单消费线程下零争用，**预期无吞吐差异**。
   - 结论：**QPS 提升主要来自更干净的测量环境，pool2/单锁不作为显著正贡献声明**。

3. **CPU 差异（-1.2%）在测量噪声内**：%usr/-system/%wait 两轮基本持平，符合「单消费线程下锁类型不影响 CPU」的预期。%system ~33.8% 与 %wait ~27.9% 仍是网络 syscall + 本机内存/磁盘压力的主体。

4. **无缺页（minflt ~0）**：两轮一致，长期稳定性结论（RSS/fd 恒定、无泄漏）不受本轮改动影响（沿用上轮 3×60s 稳定性数据）。

---

## 4. 结论

- **`db.pool_size=2` + 单锁改造是纯正向简化**：功能/吞吐/CPU 无回归（差异在噪声内），**内存净省 ~20MB（-25%）**，代码更简单。
- 连接表 16 片分片锁按设计保留（双线程访问），未纳入本次简化。
- 建议：该配置可作为 8 实例部署的正式基准；后续如需量化「干净环境下单锁的真实吞吐上限」，可在负载 ~0.2 时补一轮完整 QPS 档位表 + 最大并发 + 稳定性复测。

## 5. 复现方法

```bash
# 1. 构建（含单锁 LocalCache/RateLimit + task_queue）
make release

# 2. 启动 8 实例（高限流 + warn；db.pool_size=2 已在 config/instance_808*.json）
mkdir -p /tmp/bench_instances
for p in 8081 8082 8083 8084 8085 8086 8087 8088; do
  sed -e 's/server.rate_limit.max_requests=100/server.rate_limit.max_requests=10000000/' \
      -e 's/server.log_level=info/server.log_level=warn/' \
      config/instance_${p}.json > /tmp/bench_instances/instance_${p}.json
  nohup ./webserver --port $p --config /tmp/bench_instances/instance_${p}.json > /dev/null 2>&1 &
  echo $! > logs/bench_${p}.pid
done

# 3. 资源采样（60s c=128×8 + pidstat）
python3 tools/bench_8instances.py

# 4. 清理
pkill -f "./webserver"; rm -f logs/bench_808*.pid /tmp/res_wrk_*.log /tmp/res_u_*.txt /tmp/res_r_*.txt
```
