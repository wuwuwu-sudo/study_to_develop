# webserver 八实例性能测试报告（2026-08-22 · 2 消费线程任务队列 ×8 + 阶段2 写异步化 + 乐观锁）

- **测试日期**：2026-08-22
- **工具**：wrk 4.2.0（~/.local/bin）+ pidstat / procfs（RSS/fd）+ redis-cli
- **服务器版本**：release 构建（C++17, epoll + **8 进程 × 2 消费线程任务队列** + SQLite 连接池 4×8 + WAL）
- **架构变更（本次，较 8/21 报告）**：
  1. `server.task_queue_consumers=2`（A/B 已采用：单实例 27k→81k，8 实例合计 +11~14%）；
  2. **阶段 2 写请求异步化**：新增 DB 工作线程池（`db.worker_threads=2`），非 GET 写请求整链（中间件+路由+DB 写+缓存失效）投到 worker 线程执行，事件循环/消费线程不被写阻塞；`db.pool_size=4`（2 写 worker + 2 读消费线程 + 余量）；
  3. **乐观锁**（并发写正确性）：订单状态机条件更新（`WHERE status=期望旧值`）、菜品编辑版本列（`WHERE version=?` 且 `version+1`）、上下架/营业状态幂等条件更新；冲突返回 409，无丢失更新。
- **本版保留优化**：批量读 + 批量发 + 超时兜底、请求保护器（有界队列+熔断+高水位降级）、日志 500ms 批量落盘、限流单锁、连接表分片锁、LocalCache 单锁、字符串直出缓存、thread_local 复用、延迟缩容
- **架构**：八实例并行（8081-8088），共享 Redis（L2）+ 共享 SQLite（WAL，单写者）
- **压测目标**：读路径（3 接口）八实例合计 QPS/延迟/最大并发/资源/稳定性 + **写路径**（订单提交异步化、菜品编辑乐观锁）验证 + 与 8/21 报告对比

## 7. 写路径验证（阶段2 异步写 + 乐观锁，单实例 8081 代表）

> 读路径（八路合计）验证吞吐上限；写路径受 SQLite 单写者限制（跨进程写天然串行），此处以单实例验证**异步写吞吐**与**乐观锁正确性**（并发冲突被安全拒绝、无丢失更新）。

### 7.1 订单提交 `POST /api/order/submit`（写异步化路径）

| 每实例并发 | 合计 QPS | p50 | p90 | p99 | 非 2xx |
|-----------|---------|-----|-----|-----|--------|
| 16   | **4,255** | 3.94ms | 18.19ms | 88% tail | 0 |
| 64   | 4,149 | 15.45ms | 60.19ms | 85.7% tail | 0 |
| 128  | 4,012 | 32.05ms | 121.60ms | 94.8% tail | 0 |

- 订单提交（含订单 + 订单项落库、缓存失效）单实例稳态 **~4.1-4.3k QPS**——受 SQLite 单写者 + 写门串行 + 每单多条 INSERT 限制；**异步化使写不再阻塞读路径**（读路径与 8/21 相比不降反升）。
- 压测共写入 ~9.96 万条订单，全程无 `SQLITE_BUSY` 错误（WAL + busy_timeout 兜底 + 写门进程内串行）。

### 7.2 菜品编辑 `PUT /api/dish/edit`（版本列乐观锁）

| 每实例并发 | 合计 QPS | 成功(200) | 冲突(409) | 冲突率 |
|-----------|---------|-----------|-----------|--------|
| 16   | 5,350 | ~23.5k | 19,300 | ~45% |
| 64   | 5,436 | ~24.4k | 19,104 | ~44% |
| 128  | 6,996 | ~30.6k | 25,363 | ~45% |

- **并发编辑同一菜品（id=4）时 ~45% 请求命中乐观锁冲突返回 409**（`{"message":"菜品已被其他操作修改，请刷新后重试","success":false}`）——多个 wrk 连接基于同一 version 读-改-写，后到者被版本列条件更新拒绝。
- **无丢失更新**：成功者使 `version` 逐次 +1（压测期间 7 → 80,103），冲突请求不改数据；这正是乐观锁的预期语义（同菜并发编辑本就该冲突，前端可刷新重试）。

## 8. 性能瓶颈与优化建议（阶段2 + 乐观锁版本）

1. **读路径峰值显著提升，但每实例仍受消费线程数限制**：shops 多轮峰值 206k（较 8/21 +15%）、dishes 187k（+11%）、静态页 136k（+24%）——consumers=2 与阶段2（写移出读路径）双收益。每实例 2 消费线程 + 2 DB worker，合计 = 8 进程 × 上限。
   - 建议：若需继续提升合计吞吐，可评估 `consumers=3` 或 8 进程 × 更多 worker（注意过订阅与内存受限）。

2. **%system ~33.4% / %wait ~27.1% 仍高**：网络 `recv/send` + 多线程调度 + 本机磁盘/内存压力。
   - 建议：`sendmsg` 多缓冲批量、`SO_REUSEPORT`；生产应在内存充足、干净负载的机器上验证（本机 3.8Gi 可用仅 ~1.2Gi，长档位 QPS 低于短档位峰值）。

3. **写路径受 SQLite 单写者上限（单实例 ~4-7k）**：订单提交 ~4.1-4.3k、菜品编辑 ~5-7k（编辑无订单项多表写，略高）。异步化解决「写阻塞读」，不解决「写入吞吐上限」。
   - 建议：写放大业务若成瓶颈，迁移 PostgreSQL/MySQL 或分库；乐观锁已在应用层保证并发写正确性，迁移后同样适用。

4. **乐观锁冲突率在高并发编辑同一行时 ~45%**：这是极端并发场景的预期行为（同菜被频繁并发编辑），正常业务冲突率远低；冲突语义（409 + 前端刷新重试）已闭环。
   - 建议：前端对 409 做「刷新并重试」或「提示用户」，避免静默失败。

5. **最大并发能力**：16384 合计并发 connect 全程 0 错误；timeout 出现在 8192+ 档（本机内存瓶颈）。8 进程分摊连接，不拒绝连接。

## 9. 优化前后对比（8/21 单消费线程任务队列 vs 本次 consumers=2 + 阶段2 + 乐观锁）

| 场景 | 8/21 单消费线程×8 | **本次（consumers=2 + 阶段2 + 乐观锁）** | 变化 |
|------|------------------|------------------------------------------|------|
| `/api/shops` 多轮峰值 | ~179k | **~206k** | **+15%** |
| `/api/dishes` 多轮峰值 | ~168k | **~187k** | **+11%** |
| 静态页 `/` 多轮峰值 | ~110k | **~136k** | **+24%** |
| 最大并发峰值 | 174.5k @ 2048 并发 | 160.8k @ 4096 并发 | 同量级（本机内存受限） |
| 稳定性 QPS（3×60s） | 144-159k | **147-165k** | + |
| 资源合计 CPU（60s c=128） | ~433.7% | **~429.8%** | 持平 |
| 资源合计 QPS（60s c=128） | ~150.4k | **~166.4k** | **+10.6%** |
| 内存（8 实例合计） | ~81.9MB（pool16） | **~65.2MB**（pool4） | **-20%** |
| 写路径 | 同步阻塞消费线程 | **异步（DB worker 池）** | 读路径不再被写阻塞 |
| 并发写正确性 | 读-改-写丢失更新风险 | **乐观锁 409 兜底** | 正确性修复 |

**说明**：
- **读路径 +11~24%**：consumers=2（进程内并行）+ 阶段2（写移出读路径）双收益；每线程吞吐 206k/16 线程 ≈ 12.9k/线程（读路径缓存命中，吞吐受 epoll/发送/系统调用约束）。

- **写正确性**：乐观锁让并发写同一行「恰好一个成功、其余 409」，消除 8 进程 + 多消费线程下的读-改-写丢失更新。
- **代价**：无新增资源开销（CPU 持平、内存反降）；仅 409 语义需前端配合刷新重试。

## 10. 复现方法

```bash
# 1. 构建（含任务队列 + DB worker 池 + 乐观锁）
make release

# 2. 生成高限流 + log_level=warn 配置并启动八实例（consumers=2 / pool_size=4 / worker_threads=2 已在 config）
mkdir -p /tmp/bench_instances
for p in 8081 8082 8083 8084 8085 8086 8087 8088; do
  sed -e 's/server.rate_limit.max_requests=100/server.rate_limit.max_requests=10000000/' \
      -e 's/server.log_level=info/server.log_level=warn/' \
      config/instance_${p}.json > /tmp/bench_instances/instance_${p}.json
  nohup ./webserver --port $p --config /tmp/bench_instances/instance_${p}.json > /dev/null 2>&1 &
done
sleep 2 && for p in 8081 8082 8083 8084 8085 8086 8087 8088; do curl -s -o /dev/null -w "$p:%{http_code} " http://127.0.0.1:$p/api/shops; done; echo

# 3. 读路径：QPS / 延迟 / 最大并发 / 资源 / 稳定性（一键全流程，自动生成基础报告）
python3 tools/run_full_bench.py --version-note "阶段2+乐观锁" \
    --out docs/performance_report_20260822_8instances_stage2_optimistic.md
# 多轮峰值（可信口径）：c=128 连跑 3 轮取均值
for i in 1 2 3; do python3 tools/bench_3instances.py "/api/shops" 8 4 "128"; sleep 4; done

# 4. 写路径（单实例 8081 代表）：
#    登录商家/用户拿 session → wrk + Lua 压测
wrk -t4 -c128 -d8s -s /tmp/wrk_order_submit.lua -H "Cookie: session_id=$USID" http://127.0.0.1:8081
wrk -t4 -c128 -d8s -s /tmp/wrk_dish_edit.lua    -H "Cookie: session_id=$MSID" http://127.0.0.1:8081
#    （wrk_dish_edit 的 Non-2xx 计数 = 乐观锁 409 冲突数）

# 5. 压测后清理：pkill -f "./webserver"
```
